
ここまでの流れを整理すると、役割ごとに大きく4つのレイヤーに分かれます。トラフィックをどう発生させるか(クロール/探索)、発生した通信をどう解析するか(スキャンエンジン)、単発チェックでピンポイントに情報を取る系(TLS・技術スタック・既知脆弱性)、そして結果をどう集約するか、です。

| カテゴリ | ツール | OSS | 備考 |
|---|---|---|---|
| トラフィック生成/探索 | ZAP Traditional Spider | ○ | 静的HTMLのリンク解析のみ。SSR向け |
| トラフィック生成/探索 | ZAP AJAX Spider | ○ | SPA向けだが状態爆発・フォーム突破の限界あり |
| トラフィック生成/探索 | Playwright(ガイド付き/LLM駆動) | ○ | 事前スクリプトは非スケーラブル。LLMに次の一手を判断させる方向で検討中 |
| 解析エンジン(核) | ZAP Passive Scan | ○ | 発生源を問わず通過トラフィックを解析。今回の中核 |
| TLS/証明書 | testssl.sh | ○ | 非侵襲、暗号スイート・証明書の設定不備 |
| TLS/証明書 | sslyze | ○ | testssl.shと同系統 |
| 技術スタック検出 | WhatWeb | ○ | フィンガープリンティング |
| 技術スタック検出 | Wappalyzer | △ | ライセンス変更済み、商用利用は要確認 |
| 既知脆弱性(CVE照合) | Retire.js | ○ | JSライブラリのバージョン→CVE照合 |
| 既知脆弱性(CVE照合) | WPScan | ○ | WordPress限定。一部モードは踏み込みすぎ注意 |
| 既知脆弱性(CVE照合) | Nuclei | ○ | テンプレートのタグ精査必須(一部は攻撃ペイロードに近い) |
| 既知脆弱性(CVE照合) | OpenVAS/Greenbone | ○ | インフラ寄り、重量級、プロファイル選定必須 |
| 探索/列挙 | Nikto | ○ | 既知ファイル/設定ミス。リクエスト数が多くレート制限必須 |
| 探索/列挙 | ffuf / gobuster / feroxbuster | ○ | ディレクトリ/ファイル探索。管理画面や設定ファイル露出の発見 |
| パッシブ偵察 | crt.sh | -(無料サービス) | 証明書透明性ログからのサブドメイン発見、対象非接触 |
| パッシブ偵察 | Amass(passiveモード) | ○ | OWASPプロジェクト |
| パッシブ偵察 | Subfinder(passiveモード) | ○ | ProjectDiscovery製 |
| パッシブ偵察 | Shodan / Censys | ×(商用) | 無料枠あり、対象非接触 |
| 結果集約 | DefectDojo | ○ | 複数ツールの結果を正規化・重複排除して集約 |

自前実装で済むものとして、セキュリティヘッダーのチェック(Mozilla Observatory相当のロジック)、DNS/メール設定(SPF/DKIM/DMARC)のチェック、`.git`や`.env`のような露出ファイルの存在確認も挙がっていました。これらは既存OSSツールに頼らず軽量なHTTPリクエスト/DNSクエリで自作しやすい部類です。

全体としてはZAPを解析エンジンの核に据えつつ、トラフィック生成側をSpider依存から脱却させる(Playwright/LLM駆動探索)、そして単発チェック系のOSSツール群(TLS・技術スタック・CVE照合・探索)をZAPと並走させて結果をDefectDojoで集約する、という構成になりそうです。ライセンス面で唯一引っかかるのはWappalyzerとShodan/Censysなので、そこだけ代替(WhatWeb、crt.sh/Amass/Subfinderの無料データ)で完全OSS化できるか、割り切って有料枠を使うか、という判断ポイントになります。
